# Inventory

家庭物品管理工具。多工作区、每个工作区一个独立 SQLite 文件，同时提供完整的命令行工具。

设计目标不是记录物品本身，而是**在物品临期时主动提示**。`alert list` 命令与桌面端
顶部横幅是这一目标的直接体现，数据库仅作为其存储层。

> 应用显示名、仓库名与格式标识统一为 `Inventory`：显示名 `Inventory`，
> 归档格式 `inventory-archive`，注册表格式 `inventory-registry`，数据目录 `inventory`。
> 格式标识是机器读的（写进归档 manifest 与 `registry.json`，读取时严格比对），
> 名字里不带厂商前缀 —— 那会让人误以为是一种私有格式。

许可证：[MIT](LICENSE)。

## 免开发环境安装（绿色版）

无需安装 Node，也无需执行 `npm install`。在源码目录执行一条命令即可生成
**自包含的可分发目录**：

```bash
npm.cmd run release
```

产物位于 `release/Inventory/`（约 370 MB，含完整 Electron 运行时）：

```
release/Inventory/
├─ start.cmd            启动入口
├─ Inventory.exe        多数环境下亦可直接运行
├─ data/                数据目录（备份与迁移只需拷贝此目录）
├─ profile/             浏览器内核缓存与锁文件，可删除，会自动重建
└─ （Electron 运行时的 dll / pak / locales 等）
```

使用与维护说明：

- **首次启动为空**。不含任何示例数据，需自行新建工作区。通过界面或命令行
  新建的工作区均为空；如需示例数据，见下文 `ws seed` 命令。
- **`data/` 位于可执行文件同级的目录中**。这是有意的设计取舍：整个目录拷贝到
  其他介质或机器后，数据与程序一并迁移，无需重新配置路径。代价是**不可将其置于
  `Program Files` 等受保护目录**——该位置无法写入，程序将降级为
  「整页置灰、仅保留设置数据目录功能」的状态，此时可通过界面底部的
  「设置数据目录」指定其他位置。
- **`release/` 已列入 `.gitignore`**，不会被提交。该目录同时是 electron-builder 的
  中间产物目录，构建脚本在结束时会清理中间产物，因此仅保留 `Inventory/`。
- **更新不会丢失数据**。获取新代码后重新执行 `npm.cmd run release`，脚本会先将
  `data/` 移出、构建完成后再放回。手工更新亦可：替换整个目录，仅保留 `data/`。
- **`start.cmd` 并非多余**。部分环境下 Electron 缺少 `--no-sandbox` 参数时
  会**静默退出**（无任何输出、退出码为 0，表现为"双击无反应"），而双击 exe
  无法附加参数，因此提供该批处理文件代为传递。
- **目录命名不使用前导点或下划线**。使用 `profile` 而非 `.profile`，使用
  `release` 而非 `_release`。绿色版面向普通用户，`data` 与 `profile` 并列时
  可直接区分"需备份"与"可忽略"。
- **构建过程完全离线**。electron-builder 默认需从 github.com 下载 Electron 发行包，
  在受限网络环境下不可用，因此脚本通过 `--config.electronDist` 指向
  `node_modules/electron/dist` 中已有的副本。相应前提是：源码目录需先执行过一次
  `npm.cmd install`。


> 或执行 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 一次性解决。

> 若环境中已设置 `ELECTRON_RUN_AS_NODE=1`，Electron 将以 Node 模式启动而不创建

## 设计取舍

| 需求 | 实现方式 |
| --- | --- |
| 多个**完全隔离**的存储空间 | 一个工作区 = 一个目录 = 一个 `.db` 文件。隔离由文件系统保证，而非 `WHERE workspace_id` 条件，因此不存在因遗漏条件而串数据的可能 |
| 同一物品出现在两个工作区 | 允许且无副作用。工作区之间互不感知，`MED-0001` 在两个库中是两个独立实体 |
| 导入导出的单位是工作区 | 导出即打包某个工作区；**导入即新建一个工作区**，不会修改既有工作区 |
| 支持 agent 自动导入 | CLI + 统一 JSON 信封 + 稳定退出码 + `--dry-run` + stdout/stderr 严格分离 |
| 临期可发现 | 分类阈值 + 关键物品放大 + 三类到期日（保质期 / 质保期 / 开封后有效期） |

**「导入 = 新建」这一约束消除了最复杂的一整块逻辑**：不存在合并冲突，无需比较
`updated_at` 判断取舍，失败时删除刚创建的目录即可完全回滚。

## 数据模型

### 一行 = 一件实际存在的物品

这是本项目最重要的一条设计决定。

早先的版本采用**「物品 + 批次」两层结构**：物品记录名称与品牌，批次记录购买日期、
到期日与价格，理由是"同一种药分两次购买会得到不同的到期日"。但在家庭场景中并不存在
「批次」这一概念——使用者看到的是一盒药，而不是一条批次记录。

现在**只有一层**：

```
items        一行 = 一件实际存在的物品，自带购买日期、到期日、价格、数量
stock_moves  出入库流水（消耗 / 领用 / 丢弃 / 过期处理的审计线索）
```

同一物品购买两次 = **两条独立记录**，各自维护自己的到期日。

| 收益 | 说明 |
| --- | --- |
| 界面直白 | 一行即一件物品，无需展开查看批次 |
| 提醒逻辑简单 | 直接按物品行计算，不需要先聚合再判断 |
| 导入导出更小 | 少一张表、少一层外键、少一个 CSV 文件 |
| 无歧义 | 「这件物品还剩几个」只有一个答案 |

包含 `batches` 表的旧版归档在导入时会**自动迁移**：每个批次展开为一条独立物品记录，
继承原物品的名称、品牌、分类、位置等属性。迁移走标准的「建新表 → 搬数据 → 换名」
流程，因此旧库缺列也不会失败。该路径有对应的回归测试。

### 「批量」是需单独开启的属性

多数家庭物品**本身就只有一件**：一瓶洗发水、一个鼠标、一本护照。为它们填写
「数量 3」既无意义，也容易填错。因此默认**不是**批量物品：

| | 普通物品（默认） | 批量物品（`--bulk` / 勾选「批量」） |
| --- | --- | --- |
| 数量 | 恒为 **1**，界面上置灰不可编辑 | 可设置，如 24 |
| 操作 | **消耗**——点击一次数量归 0 | 领用 N 个，可多次 |
| 最低库存 | 无意义（自动为 0） | 可设置，低于该值即进入待补货 |
| 补货提醒 | 不参与 | 参与 |
| 典型物品 | 药品、护照、保单、滤芯、鼠标 | 抽纸、洗衣凝珠、电池、口罩、咖啡豆 |

该不变量**在写入层强制**，而非仅在界面上禁用输入——否则 CLI、JSON 批量录入与
CSV 导入均可绕过：

- 非批量物品：`quantity` 恒为 1，`remaining` 只能为 1 或 0，`min_stock` 归 0
- 部分更新时会结合库中旧值判断，因此「仅修改名称」不会把批量物品误判为非批量、
  也不会抹掉其数量

### 已移除：物品编号与到期类型

以下两处「要求用户做选择、但该选择没有实际价值」的设计已移除：

| 已移除 | 原因 | 现行表达方式 |
| --- | --- | --- |
| **物品编号**（`MED-0001`） | 家庭场景中不会有人记忆编号，填写反而是负担 | 内部保留标识供命令行定位；**界面不显示，导出包中也不含**，导入时按分类前缀重新生成 |
| **到期类型**（精确到日 / 只到月份 / 无到期） | 三选一实质是在问「是否确切知道具体日期」 | 填写日期即为该日；不填即为**长期**。包装只印到月份的，填该月最后一天 |

### 品牌 / 型号 / 规格：三个独立选填字段

这三者在录入时最易混淆，其职责划分如下：

| 字段 | 回答的问题 | 示例 |
| --- | --- | --- |
| **品牌** | 制造商 | 芬必得 / Anker / 罗技 |
| **型号** | 具体款式 | MX Master 3S / A1287 / M8R-FLP |
| **规格** | 单份容量 | 0.3g×20粒 / 20000mAh / 3层×120抽 |

三者**均为选填**且互不影响：只填其一、任意组合或全部不填都完全正常，任一字段不会被
其他字段连带修改或覆盖。

三个字段对所有物品一视同仁地开放，不做「仅数码类显示型号」式的按分类收窄——
多一栏空输入框的代价，远小于「需要填写时该字段恰好不存在」。

型号会进入导出包并原样还原（对空值敏感：原本为空，导入后仍须为空，不能变成空字符串）。
搜索也会匹配该字段：`item list --search 'MX Master'` 可命中。

### 「长期」是一种状态，不是独立档位

不设任何到期日期的物品（护照、雨伞）统一称为**长期**：

- 不参与任何到期计算，不计入「已过期 / 15 天内」的统计
- 在分组页排列于每组末尾，以一行灰色文字表示
- 该状态由「是否存在到期日期」**推导得出**，不是需要用户填写的字段

注意「是否存在到期日期」的范围宽于「是否有保质期」：只填写了**质保到期日**的鼠标
不算长期——它确实有需要记录的日期，只是该日期到达时称为"过保"而非"过期"（见下节）。

### 过期与过保：两个独立概念，分别统计

到期分为两类，**按日期来源自动判定，无需额外填写字段**：

| | 来源 | 含义 | 是否需要处理 |
| --- | --- | --- | --- |
| **过期** | 保质期、开封后有效期 | 物品已变质，不可食用或使用 | 需要 |
| **过保** | 质保期 | 物品仍可使用，仅不再享受免费维修 | 视情况而定 |

早先版本将两者合并为一个「已过期」计数，导致**"鼠标保修到期"与"药品过期"同时标红**，
真正需要处理的物品反而被稀释。因此：

- 顶部高亮、概览卡片与 `alert` 的计数**仅统计「过期」**
- 过保**单独一列**（`warrantyExpired`），在分组标题上以中性色标记表示
- 列表中的红点与红字同样只反映「过期」——仅有过保日期的物品不会标红
- 一件物品可以**同时**存在一条过期与一条过保记录（药品既有保质期也常带质保），
  二者各自归类

命令行中可直接区分：

```bash
inventory alert list --json | jq '.data.counts'
# { "expired": 3, "soon": 4, "warrantyExpired": 1, ... }
#                      ↑ 仅统计过期      ↑ 过保单列
```

### 「快到期」窗口为 15 天

顶部横幅、概览卡片与分组标题中的「N 天内到期」，窗口为 **15 天**
（`core/alerts.ts` 中的 `SOON_DAYS`，为唯一真相来源）。

- 第 15 天计入，第 16 天不计入
- **不含过保**——保修剩余 10 天不属于需要立即处理的情况
- 不含已过期物品（那由另一个计数表达）

### 简明视图

物品页与分组页各有一个「简明视图」开关，开启后仅保留两类物品：
**已过期的**与**15 天内到期的**。

该功能是**筛选开关，而非独立页面**：开启即筛选，关闭即恢复，当前的分组层级、排序、
列设置与展开状态均不受影响。

- 按钮上直接显示剩余条数（`简明视图（7）`），避免开启后为空还需再次关闭
- 纯本地筛选，不发送请求，即时生效
- 仅过保的物品**不会**出现在简明视图中，否则「简明」失去意义

物品页另有独立的「只看已过期」勾选项，两者互不冲突：简明视图针对"需要处理的"，
只看过期针对"已经变质的"。

### 提醒分级已取消，改为「分组 + 排序」

早先版本设有「已过期 / 紧急 / 临期 / 关注 / 待补货」五个档位。实测表明档位边界
（21 天算紧急还是临期）对用户没有意义，真正有效的信息只有两条：
**是否已过期**、**还剩多少天**。

因此现行为：

- **仅保留「已过期」一个标记**，其余优先级通过**排序**本身表达
- 分档列表改为**分组 + 组内排序**
- 「待补货」仍为独立段落——它属于另一类问题（数量不足），而非到期问题

### 分组、排序与手动顺序：三项互相独立的机制

三者各司其职，界面上也刻意让当前生效的机制一目了然。

| | 含义 | 修改方式 |
| --- | --- | --- |
| **分组** | 固定按**分类**一级 | 已无层级按钮，即"一个分类一组" |
| **排序** | 组内物品按哪一列排列 | **点击列头旁的 ▲ / ▼**。默认为不排序（即手动顺序） |
| **手动顺序** | 未排序时由拖动固定下来的顺序 | 拖动物品行（**仅该组未被排序时**可拖） |

三者的相互关系：

- **排序以分类为单位**。药品按到期排序与日用品按名称排序可以同时成立、互不影响；
  未被点击过的分类仍保持手动顺序
- **排序仅影响组内物品的顺序**。它不改变分组、不改变组间顺序，也不修改
  `sort_order`——因此取消排序后会**原样恢复**到手工排列的状态
- **已排序的分组禁用拖动**，拖动结果会被立即覆盖，保留可拖状态只会造成误解
- **组顺序按层级各自独立**：每一级均可拖动，结果保存在工作区注册表中

取消某一组的排序：**再次点击同一个箭头**。该组回到手动顺序，拖动同时恢复。

排序字段（`inventory sort fields` 亦可列出）。
**箭头指向哪个方向即按哪个方向排序**——下表的"默认方向"仅是命令行 `--sort`
未附带 `--desc` 时的取值，界面不受此限制：

| 字段 | 默认方向 | 说明 |
| --- | --- | --- |
| `manual` | — | 默认。按拖动固定下来的顺序 |
| `expiry` | 升序 | 最先到期的排最前，长期排在最后 |
| `name` | 升序 | |
| `category` | 升序 | 按分类的**中文名**排序，而非存储用的英文 key |
| `brand` / `model` | 升序 | |
| `purchased` | 降序 | 最近入库的排最前 |
| `quantity` / `remaining` | 降序 | 数量多的排最前 |
| `location` | 升序 | 房间 + 柜格 |
| `spec` / `notes` | 升序 | |
| `price` | 降序 | 价格高的排最前 |
| `created` | 降序 | 最近添加的排最前 |

### 「未分类」：置顶且不可拖动

分类**可以留空**，留空即为未分类。该分组的行为：

- **始终位于所有分组之上**，不受排序字段与组顺序拖动的影响
- **不可拖动**，界面上不提供拖动手柄，仅有一个 📌 标记
- 顶部另有一条提示条，显示尚未分类的物品数量

该设计是有意为之：若未分类可以像其他分组一样被拖至角落隐藏，
「还没想好放哪」将成为一个可以无限拖延的状态。置顶且不可移动，
意味着每次打开分组页都会收到一次提醒。

命令行中 `item add --unclassified` 会显式清空分类，`item list` 结尾也会提示
尚未分类的物品数量。

### 顺序号（`sort_order`）

每条物品带有一个**不展示的序号** `sort_order`，它决定默认状态下的排列位置。

- 界面不显示该数值，显示的是其在列表中的**位次**（分组页物品行最左侧一列）
- 新增物品自动排到末尾
- 拖动与 `item reorder` 修改的都是该字段
- 排序开启时它被忽略但**保留**，因此随时关闭排序都能恢复原状
- 拖动落库为**整份覆盖**而非「移动到某条之前」：整份写入是幂等的，
  拖动的中间状态与重复请求都不会打乱顺序

```bash
inventory item reorder 护照                 # 移到最前
inventory item reorder 雨伞 --after 布洛芬  # 插入到指定条目之后
inventory group list                       # 界面上的形式：按分类一级
inventory group list --levels 3            # 命令行仍可获取三级（分类 > 子类 > 标签）
inventory group list --sort expiry         # 组内按到期时间
inventory group list --order '=daily,medicine'   # 固定第一层的组顺序（会被持久化）
```

> 界面上的分组固定一级（只按分类）。`--levels` 是给命令行与脚本用的 ——
> 二级、三级看着是"更细的视角"，实际只是把同一批东西拆成更多更小的组，
> 每组两三行，翻起来更累；标签尤其糟，一个物品有多个标签就会出现在多个组里，
> 同一个东西重复出现让人怀疑是不是记了两遍。
> 分类、子类、标签这三个**字段都还在**（导出、搜索、筛选照样用）。

### 表格列可配置，但两列不可关闭

物品表显示哪些列由用户决定——界面上为物品页工具栏的「列设置」，命令行为
`column set`。**「物品」与「到期时间」为必显列，对应勾选框处于禁用状态。**

这并非限制，而是因为这两列被关闭后该表将不再成立：

- 缺少「物品」，则无从判断到期时间是**针对哪件物品**
- 缺少「到期时间」，该表将退化为普通清单——而本工具的核心目标正是
  "在临期时主动提示"

该约束实现在**数据层**（`resolveColumns()`），而非依赖界面禁用勾选框：
即使有人直接修改注册表，或后续新增了"全不选"按钮，读取结果中这两列依然存在。
这与"未分类永远置顶"属于同一类做法——关键约束不依赖调用方自觉。

| 列 | 内容 | 可否关闭 |
| --- | --- | --- |
| **物品** | 名称 + 处方 / 批量 / 长期标记 | 否 |
| **到期时间** | 到期日 + 剩余时间，同一单元格内上下两行 | 否 |
| 分类 / 品牌 / 型号 / 数量 / 购买日期 | 各自一列 | 是 |
| 位置 / 规格 / 备注 | 默认**不显示**，收纳于展开区 | 是（可手动开启） |

**「剩余时间」不是独立一列**，而是由 `到期日 − 今天` **计算得出**：

- 不单独配置，随「到期时间」一同出现——否则会出现"开启剩余时间却关闭到期日"
  这种自相矛盾的状态
- 自身随时间变化。今天显示"剩 7 个月"，明天即为"剩 6 个月 29 天"
- **刷新时机**：零点、程序启动、修改到期时间

零点刷新由主进程定时广播触发（每次触发后重新计算距下一个零点的间隔，而非固定
24 小时轮询——后者在夏令时切换或系统时间调整后会持续偏移）。此外窗口重新获得
焦点时也会比对一次日期：系统休眠一夜后唤醒，定时器不保证准时，仅依赖它会遗漏。

配置**按工作区分别保存**，存于工作区注册表，**不进入导出包**——它描述的是
"如何查看该表"，而非任何单件物品的属性。导入产生的副本使用默认列。

```bash
inventory column list                          # 查看有哪些列、当前开启哪些
inventory column set name expiry quantity      # 仅保留三列
inventory column set --default                 # 恢复默认
inventory column set --show-all                # 全部开启
```

生效范围为物品页、分组页与概览页的「最先到期」——三者为同一份物品清单，
列不一致会让人误以为看到的是不同数据。概览页的「待补货」表**不**跟随该配置：
它仅有 5 列且与到期无关，强行套用无关配置反而不合理。

### 展开区：按需显示的信息

表格每行最左侧有一个小箭头，**展开后在行下方显示**该物品的补充信息。
默认仅占一个箭头的宽度——多数场景下只需要浏览"什么物品、何时到期"。

展开后可直接查看并修改：

| 固定三项 | 说明 |
| --- | --- |
| **位置** | 分为「房间」与「容器 / 柜格」两格填写 |
| **规格** | 选填 |
| **备注** | 多行文本 |

**此外可添加任意数量的物品专属字段。** 空调记录「滤网型号」、保单记录「保单号」、
净水器记录「滤芯到期」——每件物品需要记录的附加信息各不相同，为此向数据库增加
列并不划算，因此存放在一个**扁平 JSON** 中（`items.extra_json`）。

「扁平」是硬性约束：值只能是字符串，**不允许嵌套**。允许嵌套后界面就需要实现递归
编辑器，而实际需要记录的内容形如"滤网型号 = M8R-FLP"这样一行一条。限制其形状后，
校验简单、界面简单，导出仍是单个 CSV 单元格。

- 修改**在离开输入框时自动保存**，不设"保存"按钮——展开区本用于随手记录，
  增加一步确认只会降低使用意愿
- 清空值等同于删除该字段（自定义字段会连同字段名一并移除）
- 按 Enter 提交（备注为多行，使用 Ctrl+Enter）

#### 位置 / 规格 / 备注为何仍是真实字段

它们**未**被归入上述 JSON。三者表面同属补充信息，但需要参与以下功能：

- 位置 → 分组、按位置排序
- 规格 → 导出、搜索
- 备注 → 导出

改为 JSON 后上述功能均需重写，而收益仅为"少三列"。因此它们保持为真实列，
**展开区只是其统一的使用入口**。自定义字段才是真正存入 JSON 的部分。

这也意味着：在展开区修改「规格」后，物品表开启「规格」列时会同步变化——
因为修改的是同一处数据。

```bash
inventory item extra 空调                                  # 查看
inventory item extra 空调 滤网型号 M8R-FLP                  # 新增 / 修改一个字段
inventory item extra 空调 滤网型号 ''                        # 删除该字段
inventory item extra 空调 container 客厅药箱                 # 位置（房间与柜格合成一个自由文本字段）
inventory item extra 空调 --set '{"a":"1"}'                 # 整份替换
inventory item add --name 空调 -c digital --extra '{"滤网型号":"M8R-FLP"}'
```

关于导出的一处细节：JSON 的**键会按字典序重排**后再存储。否则同一份内容因键顺序
不同会产生不同字符串，"往返后逐字相等"这一断言将无法验证。

### 「一组库存」：批量物品的嵌套条目

一件开启「批量」的物品，如果**分几次买、每批到期日不同**，可以拆成若干条**库存条目**，
每条自带数量与到期日：

```
抽纸巾（批量）
├─ #1  10 包  到期 2029-04-30  山姆
├─ #2   8 包  到期 2030-04-30  山姆
└─ #3   6 包  长期             京东
   合计 20 / 24 包，父项到期日取「还有剩余的组里最早的那个」
```

也可不拆分——单次购入的批量物品直接使用自身的数量与到期日即可。
仅在需要分别管理到期日时拆分（界面上为「拆成一组库存」，命令行为 `item stock add`）。

- **领用按先到期先出（FEFO）**：自上而下依次扣减，最先到期的一组先被扣完
- 父项的数量、剩余与到期日**全部由库存条目汇总**，不单独维护；某组用尽后，
  父项到期日自动变为下一组，不会对着一组空库存持续提示「快到期」
- 实现上，库存条目即 `items` 中 `parent_uuid` 指向父项的子行，
  因此归档格式仍只有两张表，往返不变式无需为它开特例

### 时间轴（**仅命令行，界面无此页面**）

将「到期」放到横向时间轴上呈现：横轴为**按天**划分的时间格，每行一件物品，
到期日落在哪一格即绘制在哪一格。

**界面上的时间轴页已移除。** 它回答的是"同一时间段内有多少物品到期"，
而该问题已由顶部横幅给出计数、分组页也按分类列出了到期时间与剩余天数——
为此单开一页（一条横向时间轴 + 28 格 × N 行的轨道）并不划算：
轨道上真正有价值的信息只有"哪些挤在一起"，而这从列表的到期日一列即可看出，
且无需横向滚动。

命令行保留该功能（脚本需要结构化数据）：

```bash
inventory timeline --category medicine
```

**范围与粒度均为固定值**：按天分格，覆盖「上周一 ~ 下下周日」共 4 周 28 天。
起点取上周一而非"今天减 7 天"，使横轴从整周开始、四周边界落在周一与周日上。
因此**不提供 `--granularity` / `--past` / `--future`**（这几个选项已移除，
文档中若仍出现属遗漏未改）。

### 清理已消耗完的记录

普通物品消耗完（数量为 0）后继续保留只会使列表变长。命令行提供 `item purge`：

```bash
inventory item purge --dry-run   # 先查看清单
inventory item purge --yes       # 执行
```

**批量物品即使数量为 0 也不会被清理**——它可能需要补货，或需要留作记录。

> 工作区列表原有一个「清理已用完 (N)」按钮，现已移除。那一列改为显示
> **待办条数**（已过期 + 15 天内到期，长期物品不计入），因为列表真正需要回答的是
> "哪个工作区有物品需要处理"，而非"哪个工作区可以收拾"。

### 界面配色

仅提供**暗色一套**，底色为纯黑 `#000000`，层次通过中性灰递进——
`styles.css` 中不含浅色变量，也没有 `prefers-color-scheme` 分支。

窗口标题栏由系统绘制，因此主进程启动时会强制设置 `nativeTheme.themeSource = 'dark'`。
**该设置是必需的**：系统标题栏跟随系统主题，若系统处于浅色模式，界面内容即使为纯黑，
标题栏仍会呈现一条浅灰色，视觉上如同两个程序拼接。

修改配色时需同时修改两处，且必须保持一致：

| 位置 | 变量 | 用途 |
| --- | --- | --- |
| `src/renderer/styles.css` | `--bg` / `--fg` | 界面主体 |
| `src/main/main.ts` | `THEME_BG` | 窗口首帧底色，用于防止白屏闪烁 |

`styles.css` 中还声明了 `color-scheme: dark`，否则系统处于浅色模式时，
滚动条、下拉框、日期选择器等**原生控件**会呈现浅色，在纯黑背景上如同补丁。

### 常见用法

```bash
# 录入：一件物品即一条记录，价格与到期日记录在该条记录自身
# 药品是「一件」，不需要写 --qty（写了也会被钉回 1）
inventory item add --name "布洛芬缓释胶囊" -c medicine --brand "芬必得" --spec "0.3g×20粒" \
                 --unit 盒 --container 客厅药箱-上层 \
                 --expires-ym 2027-03 --unit-price 19.30 --store 京东健康

# 同一个东西又买了一盒、到期日不同 → 再 add 一条，两条各自管自己的到期
inventory item add --name "布洛芬缓释胶囊" -c medicine --expires-on 2026-10-15

# 批量物品：确实要按个数管理时才开 --bulk，这时数量才有意义
inventory item add --name "抽纸巾" -c daily --bulk --qty 24 --remaining 24 --min-stock 6

# 查：15 天内到期的、低于下限的
inventory alert list --within 15
inventory item list --low-stock
inventory item list --expiring 60 --category medicine

# 用：普通物品一次消耗掉；批量物品可领用若干
inventory item consume MED-0001                              # 数量归 0
inventory item consume DAY-0001 --qty 3                      # 24 → 21
inventory item consume MED-0002 --reason expired_dispose     # 过期处理

# 一键清理已消耗完的普通物品（批量物品不会被清）
inventory item purge --dry-run
inventory item purge --yes

# 批量录入：写一个 JSON 数组文件
inventory item add --json-file 购物清单.json
cat 购物清单.json | inventory item add --stdin

# 维护
inventory ws stats
inventory ws verify
inventory export -o D:\备份\家当.zip
inventory import D:\备份\家当.zip --dry-run      # 先看报告
inventory import D:\备份\家当.zip --name "父母家"
```

批量录入的 JSON（键名同时接受列名与驼峰写法）：

```json
[
  { "name": "创可贴", "category": "medical_device", "brand": "云南白药",
    "spec": "100片/盒", "unit": "盒", "container": "客厅药箱-下层",
    "qty": 1, "minStock": 1, "expiresYm": "2028-06", "unitPrice": "29.90" },
  { "name": "洗手液", "category": "daily", "brand": "蓝月亮",
    "unit": "瓶", "container": "卫生间镜柜", "qty": 2, "remaining": 2, "minStock": 2,
    "notes": "补充装在储物间" }
]
```

支持的键（下划线列名与驼峰写法都可以，已逐键实测）：`name` `category` `subcategory`
`brand` `model` `spec` `unit` `barcode` `container` `sortOrder` `photo_path` `quantity`
`remaining` `minStock` `unitPrice` `amount` `store` `purchasedOn` `expiresOn` `expiresYm`
`openedOn` `openShelfLifeDays` `warrantyMonths` `warrantyUntil` `serial` `status`
`is_bulk` `prescription` `tags` `notes`

两点需要注意：

- **无法识别的键会被静默丢弃**，不报错。键名写错（例如把 `container` 写成已废弃的
  `room`）不会有任何提示，只是该字段没有写入——提交前用 `--dry-run` 核对更稳妥。
- **非批量物品的 `minStock` 会被归 0**。这是写入层强制的（非批量物品数量恒为 1，
  最低库存没有意义），并非参数未生效；需要设置最低库存时请同时加 `"bulk": true`。

### 给脚本与 agent 的约定

1. **`--json` 时 stdout 只有一个 JSON 对象**，日志全部走 stderr
2. 统一信封：

   ```json
   { "ok": true, "data": { }, "warnings": [], "meta": { "app": "Inventory", "tookMs": 42 } }
   ```

3. **稳定退出码**：`0` 成功 / `1` 运行错误 / `2` 参数错误 / `3` 数据校验失败 / `4` 未找到
4. 所有写操作支持 `--dry-run`，先看清要发生什么
5. **永不交互**：需要确认的地方一律要 `--yes`，缺参数直接报错而不是等待输入

```bash
# agent 把归档导入成一个新工作区
inventory import ./household-inventory-2026-02-14.zip --name "父母家" --json
# → { "ok": true, "data": { "workspaceId": "ws_...", "rowCounts": { "items": 187, ... } } }

# 有错误时退出码 3，且一个字节都没写入
inventory import ./x.zip --dry-run --json

# 用 jq 提取
inventory alert list --within 30 --json | jq '.data.counts'
```

## 数据布局

数据放在**程序运行目录下的 `data/`**，一个工作区一个子目录：

```
<程序目录>\data\                          ← 可用 INVENTORY_HOME 覆盖
├── registry.json                       工作区注册表（原子写入）
├── workspaces\
│   └── ws_01JG8K2M4P7QX9\               一个工作区 = 一个子目录
│       ├── data.db                     这个工作区的全部数据
│       ├── data.db-wal / -shm          WAL 日志
│       ├── meta.json
│       ├── attachments\                照片、序列号截图
│       ├── backups\                    滚动快照
│       └── import_report.json          来源审计（若由导入创建）
├── exports\                            默认导出位置
├── backups\                            删除工作区前的兜底快照
└── logs\
```

**拷贝整个 `data/` 目录就等于搬走了全部数据** —— 没有注册表、环境变量、
绝对路径之类的隐形依赖。这也是把数据放在程序目录而不是
`%LOCALAPPDATA%` 的原因。

`<程序目录>` 是往上找 `package.json` 得到的（开发时就是仓库根目录）；
打包后是 exe 所在目录。**不用当前工作目录** —— 双击图标启动时 cwd 可能是
`C:\Windows\System32`，跟着它走数据会散到系统目录里。

程序若装在 `Program Files` 这类**受保护目录**里会写不进去。这时应用会进入降级态：
**整页置灰、功能全部禁用**，只在底部「数据位置」那条上高亮提示并给出设置入口 ——
写不进去的情况下，让用户逐个去撞保存失败的报错没有意义。

也可以在命令行或环境变量里指到别处：

```powershell
# 界面里点「设置数据目录」，或命令行：
inventory config data-dir D:\我的家当

# 也可以用环境变量（优先级最高）
$env:INVENTORY_HOME = 'D:\我的家当'
```

### SQLite 配置

```
journal_mode = WAL          并发读 + 崩溃安全
synchronous  = NORMAL       WAL 下的安全/性能平衡点
foreign_keys = ON           默认是 OFF，忘了开约束就形同虚设
busy_timeout = 5000         CLI 与 GUI 同时访问时宁可等待
temp_store   = MEMORY
cache_size   = -16000       16 MB
auto_vacuum  = INCREMENTAL  建库时设定
user_version = 3            驱动结构迁移
```

其他硬规则：主键用 **UUIDv7**（时间有序、跨工作区不碰撞）；金额一律存**整数分**；
`updated_at` 由触发器维护。

> **快照为什么不用 `node:sqlite` 的 `backup()`**
>
> 实测在 Windows 上 `backup()` 会**泄漏源库的文件句柄**：`close()` 之后源库仍被占用，
> `rmSync` 永远报 `EPERM`。而"删除工作区前先留快照"恰恰最需要随后能删掉源库 ——
> 这个 bug 让删除工作区在 CLI 和桌面端都直接失败过。
>
> 现在改为「先 `wal_checkpoint(TRUNCATE)` 把 WAL 并回主库，再做字节拷贝」。
> 前提是拷贝时无其他写者（同进程串行、且调用前已 close 连接）。
> 若将来出现多进程并发写入，需要换成别的方案。

> **Windows 上删目录要带退避重试**
>
> 关闭 SQLite 连接后文件句柄是**异步**释放的，紧接着的同步 `rmSync` 容易撞上 `EPERM`。
> `removeDirWithRetry()` 对 `EPERM`/`EBUSY`/`ENOTEMPTY` 做几次退避重试，而不是一次就放弃。

## 导出包格式（本项目的公共接口）

```
household-inventory-2026-02-14.zip
├── manifest.json      机器可读：结构、类型、约束、枚举、外键（由 fields.ts 派生）
├── README.md          人可读：同一份 manifest 渲染出的字段说明表
├── checksums.txt      每个文件的 sha256
├── tables/
│   ├── items.csv
│   └── stock_moves.csv
├── attachments/       附件（可选）
└── import_report.json 该工作区当初的来源（可选）
```

### 单一真相：`src/core/fields.ts`

字段定义只写一次，三处产物全部由它派生，因此**在物理上不可能 drift**：

```
src/core/fields.ts  ──┬──► SQLite DDL          (schema.ts)
                      ├──► manifest.json       (manifest.ts)
                      └──► 界面表单与列        (renderer，经 IPC)
```

改字段只需改一处，导入导出格式与界面自动跟上。

### CSV 约定

| 项 | 值 | 原因 |
| --- | --- | --- |
| 编码 | UTF-8 **带 BOM** | 否则 Excel 打开中文乱码 |
| 引号 | **非空字段全部加引号** | 防 Excel 把 `2027-03` 当日期、把 `0012345` 的前导零吃掉 |
| 换行 | CRLF | Excel 友好 |
| 空值 | **空单元格** | 见下 |

> **空值设计说明**
>
> 最初用 `\N` 作"显式置空"哨兵，结果往返测试失败：CSV 里只有"空单元格"一种表示空的手段，
> 所以 `NULL` 与空字符串在导出时**本来就会塌缩到一起**，写哨兵并不能让信息守恒，只是让文件变脏。
>
> 语义上也不需要它：导入始终新建工作区，每行都被完整物化，不存在"部分更新"，
> 所以"空单元格 = 空值"是正确解读。现在 `\N` 仅作为**读取时的兼容**保留，**永不写出**。

`expiry_precision = 'month'`（包装只印到月，如 `2027-03`）会折算成**当月最后一天**，
因为过期判断只认 `expires_on` 一列 —— 宁可晚一天提示，也不提前误报。

### 校验与失败处理

```
安全解压（防 zip slip，逐个校验路径未逃出目标目录）
  → 校验 manifest 格式与版本兼容
  → 校验 checksums.txt
  → 逐表解析 CSV（类型转换失败报出表名与行号）
  → 必填 / 枚举 / 日期 / 编码唯一 / 外键引用 全量检查
  → 有错误：退出码 3，一个字节都不写
  → 无错误：建新目录 → 单事务写入 → 原子更新 registry → 写 import_report.json
  → 任何一步失败：删除刚建的目录，注册表未动过
```

## 提醒规则

分级：`已过期` → `紧急`（≤ 阈值/3）→ `临期`（≤ 阈值）→ `关注`（≤ 阈值×2）→ `正常`

阈值按分类，**刻意收得比较紧**：

| 分类 | 提前量 | 理由 |
| --- | --- | --- |
| 药品 / 保健品 | 60 天 | 家里翻药箱的周期长，值得早提醒 |
| 食品 | 15 天 | 提前太多没意义，"还剩几天"更有用 |
| 日用品 / 化妆品 | 45 天 | 够在下次采购时补上 |
| 数码 / 医疗器械 | 60 天 | 质保到期前要留出送修时间 |
| 证件票据 | 45 天 | 续保/换证要预约 |

标记为**关键物品**的条目，窗口 ×1.5。

> 阈值过大会让列表被噪音填满，用户约三周后便会忽略它——届时整个提醒机制即告失效。
> 第一版把证件类设成 120 天（关键物品后变 180 天），交强险提前半年就报"紧急"，
> 实测后收紧到 45 天。

三类到期日**同时参与**提醒：

1. **保质期** —— `expires_on`
2. **质保期** —— `warranty_until`
3. **开封后有效期** —— `opened_on + items.open_shelf_life_days`（很多药开封后远短于保质期）

## 已知限制

- **zip 依赖系统 `tar.exe`**（Windows 10 1803+ 自带）。打包后的应用同理。
  换成自实现 zip 或引 `fflate` 即可解除，但会引入依赖，当前取舍是保持零依赖。
- `node:sqlite` 在 Node 下会打印 `ExperimentalWarning`（走 stderr，不影响 stdout 的 JSON）。
  设 `NODE_NO_WARNINGS=1` 可静音。
- **桌面端表格未做虚拟滚动**，几百行无压力，上万行需要分页。命令行不受影响。
- 尚无条码扫描与小票 OCR —— 需要时再加，不影响现有格式与命令。
- 桌面端与命令行共用 `src/core/`，但**没有做并发写的协调**：
  两边同时改同一个工作区时，SQLite 的 WAL 能保证不损坏，但后写的一方会覆盖先写的字段。
  单人使用场景下无影响。
- **打包（`dist:win`）尚未验证过**。功能层面是验过的，产出安装包这条路没走过。
  走通的是 `npm.cmd run release` → `release/Inventory/`（绿色版，双击即用）。
- **「字段与格式」页从界面上点不进去。** `wireChrome()` 只给 `.tab:not(.hidden)`
  绑点击事件，而这一页的页签是隐藏的 —— 它连监听器都没有。那一页本来就只是
  排查问题时看的（`schema show` 命令照常可用），所以走查验的是它背后的数据。
- 用脚本起 Electron **必须加 `--no-sandbox`**，否则进程会静默秒退
  （退出码 `0x80000003`），很容易误判成代码有问题。
- 「剩余时间」是算出来的，跨天靠零点定时器 + 窗口焦点检查刷新（另加 60 秒自检）。
  定时器在系统休眠期间不保证准时，所以焦点检查是必要的兜底 ——
  但极端情况（手动改系统时间后一直不碰窗口）下可能要切一下页签才会重算。
